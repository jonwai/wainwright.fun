# @wainwright/local: tickets, wainwright.fun and admin on the home network

`tickets.wainwright.fun`, `wainwright.fun` and `admin.wainwright.fun` served from the Mac Studio (Wainsburys/local docker compose service `tickets`, `Dockerfile.local` at the repo root), on the shared Postgres database. Hosted (CDK stacks, Lambda, DynamoDB) is untouched; nothing here deploys anything.

- **Handlers.** `src/routes.ts` runs the hosted `packages/infra/lambda/task-routes.ts` unchanged. `src/pg-ddb.ts` (`PgDocumentClient`) answers its DynamoDB document-client calls (Get/Put/Delete/Query/Scan on tasks, task-completions, job-board, rewards, reward-redemptions, term-dates) from schema `tickets` and `core.term_dates`; anything else throws. `build.mjs` swaps the hosted `kid-routes` and `budget-routes` imports for `src/shims/` (no device tokens, no Wainsbury's budget).
- **Schema** (`migrations/001_tickets.sql`): `tickets.tasks`, `board`, `awards`, `rewards`, `redemptions`, view `balances`; children are `core.people` ids (foreign keys and a trigger for `assigned_to`). Spendable = all awards − all redemptions, as hosted. `tickets.award(...)`/`tickets.revoke(...)` let another app (household) award tickets in its own transaction; those awards cannot be edited or deleted through the tickets API.
- **Reward paper** (`src/household-inventory.ts`). A reward with `extra.household_consumable` (`{ category, sheets }`, for example `printer-paper` and `10`) asks the parent to pick a Household product when they claim the redemption. `printer-paper` calls `HOUSEHOLD_URL` (compose: `http://household:43126`). `GET /api/integrations/tickets/printer-paper?min_sheets=` returns `{ papers: [{ product_slug, name, sheets_remaining }] }` (a bare array is accepted too); 400 means `min_sheets` was bad. `POST .../printer-paper/use` sends `{ product_slug, sheets, ref, source: "tickets-reward" }`. The ref is the Tickets redemption id: it has no `#`, and a refund deletes that row, so a later redeem is a new id. The same ref with the same product and sheets returns `already: true`. A different product or sheet count, or a ref that was already reversed, is 409. 400 means the product is not paper or has no pack size, 404 means Household doesn't know it, and 409 means not enough sheets or that ref clash; those are shown on the claim. 401 means the service token was refused and is a separate warning; the claim still stands. If Household is quiet or has nothing, the claim still goes through and the admin says the stock wasn't reduced. Refunding a recorded use is only `POST .../printer-paper/reverse` with `{ ref }`. The first answer is `{ restored: true, already: false }` and a repeat is `{ restored: false, already: true }`; both are success. Every call sends `Authorization: Bearer`. The token is `HOUSEHOLD_SERVICE_TOKEN`, or the trimmed contents of the file named by `HOUSEHOLD_SERVICE_TOKEN_FILE`. On the Mac, in `~/Documents/GitHub/local/docker-compose.yml`, mount `~/.config/household/service-token` read-only into the tickets service and set `HOUSEHOLD_SERVICE_TOKEN_FILE` to that path. Editing the reward in admin keeps `household_consumable`.
- **House chores** (`src/household-chores.ts`). Off unless `HOUSEHOLD_CHORES=1` and `HOUSEHOLD_URL` is set (compose: `http://household:43126`, same Docker network, no token). The kid list is `GET /api/kid/chores?child=<core.people.id>` with header `X-Household-Child` set to that same id. Tickets shows chores whose `claim.child_id` is that child (including locked ones; `waiting_on` is joined for display) and completions where `last_completed_by_me` is true within the last 24 hours. When Household sends `chores` and `done_recently`, those lists are used instead. Done and undo are `POST /api/kid/chores/{id}/complete|undo` with that header and `{"child_id"}`. The kid app does not offer claim. The badge is Household's `tickets`. Tickets does not read `household.*` and does not call `tickets.award`. If Household is down or the flag is off, the section is hidden and the jobs list is unchanged.
- **Identity** (`src/identity.ts`, the same code as Snacks): by client IP from `core.devices` (Caddy's `X-Real-IP`). Kid devices: that kid only, never the admin. Parent devices: admin plus "act as" any child. Unknown: "This device isn't set up", no data. No sign-in, pairing or tokens.
- **Every API request is one transaction**; writes take an advisory lock, so two redeems cannot overspend.
- **Front ends.** The kid app (`apps/tickets`, built with `VITE_LOCAL_AUTH=1 VITE_API_URL=/api` into `dist-local`) and the admin's Tickets panel alone (`apps/admin/local-tickets.html`, `vite.local-tickets.config.ts`, served at `/admin/`).
- **Import** (`src/import-hosted.ts`): from read-only scans of the six hosted tables; mirrors the library, upserts hosted awards and redemptions, keeps local ones, and commits only when the result matches hosted item for item with equal balances. Idempotent. See Wainsburys/local README "Tickets". Since the DNS switch (8 Oct 2026, 12:04 BST) the local tables are live: use `--stragglers-since <scans imported at the switch>`, which only adds hosted awards and redemptions that are new since then and commits only if every existing row is unchanged; the full import would undo local changes to hosted-sourced rows.
- **wainwright.fun and admin.wainwright.fun** (`src/sites.ts`, `src/kids.ts`; dispatched on Host). `wainwright.fun` and each child's hostname (`{id}.wainwright.fun` when that id is a child in `core.people`, plus any extra names in `KIDS_LAUNCHER_HOSTS`) are the launcher. The child is still the device's IP, not the hostname, so a bookmark such as `hannah.wainwright.fun` reads this database once that name reaches the Mac. `www` redirects to the apex. Anything else is tickets. The hosted `api`, `auth`, `chores` and `twin` names were retired on 11 Oct 2026. The launcher (`apps/kids` built with `vite.local.config.ts`, `VITE_LOCAL_AUTH=1`): the child is the device's IP; a parent's device picks a child (host-only `tickets_act_as` cookie); no pairing, and the hosted device token stored on an iPad is neither sent nor cleared. `/kid/config` and `/kid/profile` are the hosted `kid-routes` logic on Postgres through the same shared generator (`buildRootConfig` → `resolveChildConfig` → `generateProfile`), so the allowlist, Web Clips and restrictions are what hosted serves for the same data. Every child also gets the Snacks, Tickets and Brush Time (`brush.wainwright.fun`, added 26 Oct 2026) Web Clips from `resolveChildConfig` (check with `packages/infra/scripts/verify-*-clip.ts`). Web Clip icons come from the `kids-icons` volume (a checked copy of the site bucket); the profile is signed with the cert and key files (the same certificate as hosted) and never served unsigned (503). Every profile handed out is recorded in `kids.profile_downloads` (rows 1–31, 8 Oct 13:44–14:18 BST, are simulated test downloads from before any DNS change). The admin (`apps/admin/local-admin.html`, `vite.local-admin.config.ts`; no Cognito) is the hosted panels for children, apps, system apps, websites, themes, restrictions and term dates (read-only; edited in Snacks), plus a Devices tab, on a parent's device only. Devices are managed on admin.wainwright.fun (`GET`/`PUT`/`DELETE /api/admin/devices`, people for the picker at `GET /api/admin/people`): label, IPv4 address, MAC address and which person in `core.people` the device belongs to. A parent can add, edit and remove devices, but not the device they are using. Not in the Snacks app. Not here: tickets (since 8 Oct 14:43 BST: managed in tickets.wainwright.fun/admin/; the admin host answers `/api/tasks`, `/rewards` and `/board` with 410), the per-child Snacks and Pairing tabs (`ChildrenPanel includeSnacks={false} includePairing={false}`; the hosted admin keeps both), pairing, chores, budgets, and deploy. Saving an app or website fetches its icon into the kids-icons directory at the path the launcher requests (`app-icons/{appStoreId}.jpg`, or `website-icons/{name}` / `{hostname}.png`); the save does not wait, and a failed download leaves the row saved. `POST /api/icons/fetch` backfills whatever is still missing (the Apps and Websites tabs have a button for it).
- **Schema** `kids` (`migrations/002_kids.sql`): `child_settings` (locked, restriction overrides, blocked apps; children themselves are `core.people`), `apps`, `websites` (`child_id` → `core.people`), `themes`, `restrictions`, `profile_downloads`. Deleting a child from the admin is refused.
- **Import** (`src/import-kids.ts`): read-only scans of the hosted children, apps, websites, themes, restrictions and term-dates tables (device tokens and pairing codes are never read); mirrors the config, reports any difference in a child's name, date of birth, colour or avatar (`--update-people` to take hosted's), compares term dates with `core.term_dates`, and commits only when every item reads back equal to hosted.
- **Proof** (`scripts/compare-hosted.mjs`): runs the deployed API Lambda bundle against DynamoDB Local (dummy credentials, no bucket, no secrets: it cannot reach AWS) loaded with the same scans, and compares each child's `/kid/config` and profile with the local code and with what the running server serves (signature verified). Run it as `NODE_PATH=../infra/node_modules node scripts/compare-hosted.mjs --bundle <index.js> --scans <dir> [--no-served-profile]`; on live data pass `--no-served-profile`, because every profile the server hands out is recorded in `kids.profile_downloads`. Since 8 Oct 2026 14:24 BST wainwright.fun and admin.wainwright.fun are served from here (Wainsburys/local README "wainwright.fun cutover"); the local `kids` tables are live, so only re-import from hosted to roll forward after a rollback.
- **Signing files** reach the container as compose secrets; `docker-entrypoint.sh` (root only for this) copies them into a tmpfs readable by the `node` user and then drops to `node`.
